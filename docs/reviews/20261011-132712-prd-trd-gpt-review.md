## 1. 종합 판정: 먼저 수정 권장

개인용 첫 버전의 목적, 출력 형태, 실패 표시, 수동 실행 범위는 비교적 구체적입니다. 다만 **데이터 이용 조건**과 **번역 엔진의 실제 접근·비용·데이터 처리 방식**이 확인되지 않아 현재 문서만으로 책임 있게 구현에 착수하기는 어렵습니다. 나머지 빈틈은 대부분 초기 실행에서 확인하거나 개선할 수 있습니다.

## 2. 막는 문제(있다면)

- **TRD > 가능성 확인 결과 / 가정 4:** Google 뉴스 RSS 응답을 확인한 것은 데이터가 기술적으로 수집된다는 근거지만, 자동 수집 및 재사용이 허용된다는 근거는 아닙니다. 하루 한 번 개인용이라는 가정만으로 이용 조건이 확인되지는 않습니다. 이용 조건을 확인하거나, 확인 전 사용할 범위와 보관·표시 방침을 정해야 합니다.
- **TRD > 가정 1:** `claude -p`가 현재 환경에서 동작하는지, 기존 구독으로 자동 호출할 수 있는지, 요약 요청에 대한 사용량·비용 및 제목 전송의 처리 조건이 어떤지 확인되지 않았습니다. 문서가 이미 작은 실험을 구현 순서에 넣었으므로, 그 결과로 번역 경로와 데이터 처리 방침을 확정한 뒤 진행하는 것이 적절합니다. API 키 방식 전환 시 사용자 확인을 받겠다는 기준은 명확합니다.

## 3. 중요한 개선점: 우선순위 순

1. **이슈 묶음·점수 검증 기준을 보완하세요.** Jaccard 임계값은 미정이고 제목에서 티커·이름 핵심 단어를 요구하면, 약칭·동의어를 쓰거나 티커가 우연히 포함된 제목을 잘못 처리할 수 있습니다. 임계값 외에도 정답 묶음 표본, 오병합·누락 판정 방법, 동점 처리의 재현성을 정하세요. 서로 다른 언론사 수가 사람이 센 값과 일치하는 완료 기준은 수집된 표본의 집계 검증에는 유용하지만, 어떤 기사가 수집되지 않았는지 또는 분류가 맞는지를 보장하지는 않습니다.
2. **뉴스가 없는 경우와 수집 실패의 경계를 정하세요.** RSS 응답은 왔지만 파싱 오류·부분 누락이 생긴 경우, HTTP 오류나 시간 초과가 난 경우, 일부 항목만 유효한 경우를 어떻게 표시할지 현재 기준으로는 판단하기 어렵습니다. 종목 단위 격리 원칙에 부분 성공의 표시 방침을 더하면 결과의 의미가 선명해집니다.
3. **운영·비밀정보 기준을 구체화하세요.** `.env`와 앱 비밀번호를 언급했지만, 저장소에서 제외하는 것 외에 로그·오류 메시지에 비밀정보가 노출되지 않는지, 발송 실패를 어떻게 알리는지, 같은 날 재실행 시 중복 메일을 허용하는지가 정해져 있지 않습니다. 개인용 수동 실행에서는 일부를 첫 실행 전에 결정해도 되지만, 자격 증명 취급과 실패 인지 방법은 발송 기능 구현 전에 정하는 편이 좋습니다.
4. **번역·요약 완료 기준을 관찰 가능하게 하세요.** 번역 실패 처리는 정의되어 있으나, 요약 응답 누락·부분 실패·출력 형식 오류의 처리 기준은 없습니다. 프롬프트에 사실 추가 금지를 적은 것은 지침이지, 그 준수 여부를 판정하는 완료 기준은 아닙니다. 표본 입력과 기대 출력 검토 기준을 정하고, 확인이 어려운 주장은 검증된 사실처럼 표시하지 않는 방침을 명시하세요.
5. **실행 환경 의존성을 확인하세요.** Python 표준 라이브러리만 사용한다는 점은 단순하지만, RSS 네트워크 접근·Claude CLI·Gmail SMTP에 PC 환경과 계정 설정이 각각 필요합니다. 실행할 Python 버전, Claude CLI 호출 가능 여부, Gmail SMTP 연결 여부는 환경 확인 항목으로 남겨 두는 것이 좋습니다. 자동 실행을 수동 실행 안정화 뒤로 미룬 결정은 합리적입니다.
6. **30초 목표의 측정 방식을 정하세요.** 목표는 종목별 주요 이슈를 보고 원문을 읽을지 판단하는 것이지만, 완료 기준에는 이를 확인할 방법이 없습니다. 예를 들어 소유자가 실제 메일을 읽고 판단 가능한지 점검하는 표본 검토를 완료 기준에 둘 수 있습니다.

## 4. 프로젝트 소유자가 결정할 질문

- Google 뉴스 RSS 이용 조건을 어디까지 확인하고, 확인 전에는 어떤 범위와 보관 방침으로 사용할까요?
- Claude CLI 실험에서 확인해야 할 항목은 무엇으로 할까요? 최소한 호출 가능성, 추가 비용 여부, 제목 데이터의 처리 조건을 기록할까요?
- 이슈 묶음의 오병합과 누락을 어느 정도까지 허용할까요? 첫 버전에서 임계값을 정할 표본과 검토 기준은 무엇인가요?
- 종목별 RSS 결과가 일부만 수집되거나 파싱되지 않은 경우, 정상 기사와 함께 부분 실패로 표시할까요?
- 같은 날 재실행할 때 메일 중복 발송을 허용할까요? 실패 알림은 어디서 확인할까요?

## 5. 필요한 경우 작고 구체적인 문구 또는 완료 기준 수정 제안

완료 기준에 아래 항목을 추가하면 구현 결과를 확인하기 쉬워집니다.

- “고정한 RSS 표본에 대해 이슈 묶음의 정답 예시를 검토하고, 병합·분리 결과를 기록한다. 임계값 변경 후에도 같은 표본으로 재검증한다.”
- “일부 항목의 파싱 또는 수집에 실패한 경우, 해당 종목을 ‘뉴스 없음’으로 표시하지 않고 부분 수집 실패임을 구분한다.”
- “번역·요약 응답이 누락되거나 형식에 맞지 않으면 빈 결과를 정상 요약처럼 표시하지 않고 실패를 표시한다.”
- “개인정보·비밀정보 항목에는 RSS 제목을 외부 번역 서비스에 전달하는지, 자격 증명을 로그에 출력하지 않는지 명시한다.”

이 보완을 마치면 나머지 미정 사항은 기록된 표본과 첫 실행 결과를 통해 조정할 수 있습니다.
