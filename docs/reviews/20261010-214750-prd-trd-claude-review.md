# 계획 검토 결과: 주식 정보 수집 프로젝트

## 1. 종합 판정: **결정 대기**

목표·사용자·범위는 한 줄씩이지만 방향이 분명합니다. 다만 구현을 좌우하는 네 가지(데이터 출처, 누락 처리, 실행 시간, CSV 컬럼·완료 기준)를 계획서가 스스로 미정으로 두었습니다. 이 중 **데이터 출처**만 실제로 착수를 막고, 나머지는 출처가 정해지면 짧게 확정할 수 있습니다.

## 2. 막는 문제

**[미정 항목] 데이터 출처와 이용 조건이 정해지지 않음**

출처에 따라 아래가 모두 달라져서, 정하지 않고 코드를 쓰면 수집부를 다시 만들 가능성이 큽니다.

- **인증 방식**: API 키나 증권 계좌가 필요한지, 비밀정보를 관리해야 하는지가 갈립니다.
- **데이터 제공 시점**: 당일 종가를 당일 저녁에 주는지, 다음 영업일에 주는지에 따라 "장 마감 후 하루 한 번"이라는 목표의 실현 가능 여부가 바뀝니다.
- **이용 조건**: 개인적 이용, 자동 수집, 저장이 허용되는지가 출처마다 다릅니다.
- **응답 필드**: 종목명 제공 여부와 종목 식별자 형식이 CSV 컬럼을 결정합니다.

후보별 조건은 이 검토에서 확인하지 않았습니다. 아래는 제 기억에 따른 것이므로 **추가 조사할 주장**입니다.

| 후보 | 조사할 내용 |
|---|---|
| 공공데이터포털 주식시세정보 | 당일이 아니라 다음 영업일에 갱신되는 것으로 알고 있음. 맞다면 "당일 장 마감 후 수집"과 충돌 |
| KRX 정보데이터시스템 Open API | 키 신청·승인 절차, 호출 한도, 갱신 시점 |
| 증권사 Open API(예: 한국투자증권) | 계좌 필요 여부, 앱키·시크릿 관리, 토큰 만료 주기 |
| 비공식 라이브러리(pykrx, FinanceDataReader 등) | 내부적으로 포털·거래소 페이지를 긁는 방식이라 이용약관상 지위가 불명확하고 예고 없이 깨질 수 있음 |

## 3. 중요한 개선점 (우선순위 순)

**① 완료 기준이 없음 (요구사항과 완료 기준)**
- 충족: "10개 종목, 평일, 하루 한 번, CSV"라는 수량·주기·형식은 있습니다.
- 보완: 성공한 하루가 어떤 상태인지 관찰할 기준이 없습니다. 5절에 문구를 제안했습니다.
- 미결정: CSV 컬럼, 파일 구조(누적 1개 파일인지 일자별 파일인지), 인코딩.

**② "평일"과 "거래일"이 다름 (요구사항)**
- 보완: 공휴일과 연말 휴장일에는 평일이어도 종가가 없습니다. 이 날을 건너뛸지, 실패로 볼지, 전일 값을 넣을지가 누락 처리 규칙의 핵심입니다.
- 추가 조사: 수능일처럼 장 시간이 바뀌는 날이 있어, 실행 시간을 마감 직후로 빠듯하게 잡으면 어긋날 수 있습니다.

**③ "종가"의 정의 (요구사항)**
- 보완: 정규장 종가인지, 수정주가(액면분할·배당 반영)인지 명시가 없습니다. 개인 확인 용도라면 정규장 원종가로 충분해 보이지만, 장기간 누적해 비교할 생각이면 분할 시 값이 끊깁니다.
- 미결정: 거래정지 종목은 값을 어떻게 기록할지.

**④ 실행 환경과 실패 처리가 언급되지 않음 (기술적 실행 가능성 / 위험)**
- 미결정: 어디서 돌릴지(개인 PC 스케줄러, 클라우드, GitHub Actions 등). PC가 꺼져 있으면 그날 데이터가 빠지므로 누락 처리와 직접 연결됩니다.
- 보완: 실패를 어떻게 알아챌지(로그, 알림), 재실행 시 같은 날짜 행이 중복되지 않게 할지, 빠진 날을 나중에 채울 수 있는지가 없습니다. 출처가 과거 일자 조회를 지원하면 대부분 단순하게 해결되므로 출처 선택 기준에 넣을 만합니다.

**⑤ 종목 목록 관리 (목표와 범위)**
- 충족: 문제, 사용자(1명), 첫 버전 범위(가격·종목명)는 분명합니다.
- 보완: 10개 종목이 무엇이고 어디에 정의하는지(설정 파일인지 코드 고정인지), 종목명이 아니라 종목코드로 식별할지가 없습니다. 사명 변경이 있으므로 코드 기준이 안전합니다.
- 보완: 제외 범위가 암묵적입니다. 거래량·시가·고가·저가, 실시간 시세, 알림, 시각화를 "하지 않음"으로 한 줄 적어두면 범위가 늘어나는 것을 막습니다.

**⑥ 보안·개인정보 (위험)**
- 개인정보는 다루지 않아 위험이 낮습니다.
- 키가 필요한 출처를 고르면 키 보관 위치(환경변수 등, 저장소 커밋 금지)만 한 줄 추가하면 됩니다. 증권사 API라면 계좌와 연결된 자격증명이므로 조회 전용 권한인지 확인이 필요합니다.

## 4. 프로젝트 소유자가 결정할 질문

1. **데이터 출처는 무엇으로 할 것인가?** 키 발급이나 계좌 연동을 감수할지, 비공식 라이브러리의 불안정성과 약관 불확실성을 받아들일지.
2. **당일 종가가 당일 저녁에 꼭 필요한가, 다음 날 오전에 받아도 되는가?** 고를 수 있는 출처의 폭이 여기서 갈립니다.
3. **어디서 실행할 것인가?** 항상 켜진 환경이 있는지.
4. **휴장일과 수집 실패일을 CSV에 어떻게 남길 것인가?** 행 없음, 빈 값 행, 나중에 채움 중 하나.
5. **CSV는 누적 1개 파일인가, 일자별 파일인가?** 컬럼은 무엇인가.
6. **종가는 원종가로 충분한가, 수정주가가 필요한가?**
7. **10개 종목은 무엇이며, 바꿀 일이 있는가?**

1~3번이 정해지면 구현을 시작할 수 있고, 4~7번은 착수 직전에 정해도 됩니다.

## 5. 문구·완료 기준 수정 제안

아래는 예시이며, 값은 소유자가 정해야 합니다.

**목표 문구**
> 국내 주식 10개 종목(종목코드로 지정)의 정규장 종가를 **한국거래소 거래일마다** 장 마감 후 1회 수집해 CSV에 누적 저장한다.

**제외 범위 추가**
> 첫 버전에서 하지 않는 것: 실시간·장중 시세, 종가 외 가격·거래량, 알림, 차트, 수정주가 보정.

**CSV 컬럼 초안**
> `date`(YYYY-MM-DD), `code`(6자리 문자열), `name`, `close`(정수, 원). 키는 `date`+`code`.

`code`를 문자열로 못박지 않으면 앞자리 0이 사라지고, 한글 종목명은 인코딩을 정하지 않으면 엑셀에서 깨집니다. 엑셀로 볼 계획이면 UTF-8 BOM을 명시하세요.

**완료 기준 초안**
> - 거래일에 실행하면 10개 종목 모두에 대해 해당 일자 행이 1개씩 추가된다.
> - 같은 날 다시 실행해도 행이 중복되지 않는다.
> - 휴장일에 실행하면 행을 추가하지 않고 정상 종료한다.
> - 일부 종목 수집에 실패하면 성공한 종목은 저장하고, 실패한 종목과 사유를 로그에 남기며 0이 아닌 종료 코드로 끝난다.
> - 연속 N 거래일(예: 5일) 동안 수동 개입 없이 위 조건을 만족한다.
